### The single most decision-relevant question: can it be embedded in a plain AppKit `NSViewController` without adopting SwiftUI wholesale?

**[V] YES — verified directly from source, not inferred.** `Sources/CodeEditSourceEditor/Controller/TextViewController.swift` (`https://raw.githubusercontent.com/CodeEditApp/CodeEditSourceEditor/main/Sources/CodeEditSourceEditor/Controller/TextViewController.swift`), line 1 of the doc comment block:

> `public class TextViewController: NSViewController`

This is a genuine `NSViewController` subclass — `import AppKit` at the top of the file, with `import SwiftUI` present only because the file also defines an `NSViewControllerRepresentable` wrapper elsewhere, not because the controller itself needs SwiftUI to exist. It exposes `scrollView: NSScrollView!`, `textView: TextView!`, `gutterView: GutterView!`, `minimapView: MinimapView!` as direct AppKit view properties, and its public initializer (`init(string:language:configuration:cursorPositions:highlightProviders:foldProvider:undoManager:coordinators:completionDelegate:jumpToDefinitionDelegate:)`) takes no SwiftUI types at all.

> (`https://raw.githubusercontent.com/CodeEditApp/CodeEditSourceEditor/424453d2232c9912933a3b5a1f3d3df669404ed0/Sources/CodeEditSourceEditor/Controller/TextViewController.swift`):
> - `public class TextViewController: NSViewController` at **line 19**, `import AppKit` at **line 8** — the
>   core claim is **CONFIRMED from the literal declaration**.
> - **But only two of the four view properties are reachable cross-module.** `scrollView` and `textView`

Separately, `Sources/CodeEditSourceEditor/SourceEditor/SourceEditor.swift` (`https://raw.githubusercontent.com/CodeEditApp/CodeEditSourceEditor/main/Sources/CodeEditSourceEditor/SourceEditor/SourceEditor.swift`) defines `public struct SourceEditor: NSViewControllerRepresentable` whose `makeNSViewController(context:) -> TextViewController` literally constructs and returns a `TextViewController` — i.e. **the SwiftUI API is a thin wrapper around the AppKit `TextViewController`, not the other way around.** The AppKit surface is primary; SwiftUI is the convenience layer bolted on top of it. A pure-AppKit consumer can `import CodeEditSourceEditor` and instantiate `TextViewController` directly, add it as a child view controller, and never touch SwiftUI. This matches the README's own claim ("An AppKit API is also available") but the claim is now grounded in the actual class hierarchy, not just README prose.

## 3. Hand-rolled: `NSTextView` + TextKit 2 + tree-sitter (`SwiftTreeSitter`) or `Highlightr`

**What it actually costs, framed against Umber's 350-LOC-per-file ceiling:**

A minimum viable hand-rolled stack needs, at minimum: (1) a tree-sitter parse-and-query pipeline (incremental re-parse on edit, byte↔UTF-16 range translation — SwiftTreeSitter handles the C API but the incremental-update orchestration is the integrator's job), (2) an invalidation/highlighting-application layer that avoids flicker on keystroke (this is precisely what ChimeHQ's Neon exists to avoid reinventing — see §4), and (3) a custom `NSRulerView`-based or overlay-view-based gutter with line-number computation that stays in sync with TextKit 2's *asynchronous, viewport-driven* layout. None of these three pieces is naturally a single ~300-line file; a credible from-scratch version is realistically 4-8 files even before language-specific query files are counted. **[I]** — this LOC estimate is a judgment call based on the componentization CodeEdit and STTextView themselves needed (each splits gutter, highlighter, layout-manager, and selection into separate files internally), not a direct line-count measurement of a hypothetical Umber implementation.

**Specific, sourced TextKit 2 pitfalls on macOS 14/15** — this is STTextView's maintainer's own bug-tracking list, accumulated over ~4 years of building directly against the framework. **[V]** Source: `https://github.com/krzyzanowskim/STTextView` README, "🐛 TextKit 2 Bug Reports List" section (each entry is a live Feedback Assistant bug ID with either a linked repro gist or inline description):

- **Viewport-layout surprises**: *FB19698121 — "TextKit 2 undocumented and unexpected behavior in `textViewportLayoutControllerDidLayout`"* (gist: `https://gist.github.com/krzyzanowskim/4d831e0f44035b605768ff9d2a4c285e`). This is precisely the API surface a hand-rolled gutter or minimap would depend on to know when to redraw.
- **Regression specific to macOS 14**: *FB14700414 — "NSTextList doesn't work since macOS 14 (regression)"*.
- **Regression, still open as of the README's last edit**: *FB15131180 — "TextKit extra line frame is incorrect and does not respect layout fragment size (regression)"* (gist: `https://gist.github.com/krzyzanowskim/510ecf8df259d779e22df8ad13c256c0`).
- **Long-line layout jump bug** (explicitly called "nasty" by the maintainer): *FB9886911 — "NSTextView can't properly layout and display long lines... causes the view to 'jump' whenever text attribute updates"*.
- **Ruler/gutter-adjacent**: *FB13290979 — "NSTextContainer.lineFragmentPadding does not affect end of the fragment usageBoundsForTextContainer rectangle"* and *FB13291926 — "NSTextLayoutManager.usageBoundsForTextContainer observer is never triggered"* (noted "Fixed again in macOS 15.6" in the current README, implying it *regressed* between fixes — a live example of the framework's instability across OS point releases).
- **Fresh 2026 entry**: *FB22524198 — "NSTextLayoutFragment.extraLineFragmentAttributes is private API that makes impossible [to] calculate extra line fragment correctly"* — this is one of the newest entries in the list (alongside FB22523964, both without gist links yet, suggesting very recent filing), meaning the pitfall surface is **still growing in 2026**, not just legacy WWDC-2021-era bugs.
- **Performance-cliff confirmation from a second, independent source**: ChimeHQ's Neon README states plainly, *"priority range calculations (the visible set for most text views) are of particular importance. This is surprisingly challenging to do correctly with TextKit 1, and extremely hard with TextKit 2."* and, in the TextKit-integration section: *"I have not yet figured out a way to do this with TextKit 2, and it may not be possible without new API."* (`https://github.com/ChimeHQ/Neon`, referring to flicker-free on-keypress highlighting). **[V]** Two independent, maintainer-level sources (Krzyżanowski and Massicotte) converge on the same conclusion: TextKit 2's viewport/invalidation model is the hard part, not glue code.

**Highlightr as the "cheap tree-sitter alternative"**: **explicitly deprecated.** **[V]** `https://github.com/raspu/Highlightr` — top of README: *"As of 2026, Highlightr is no longer actively maintained. We recommend using HighlighterSwift instead."* Last release 2.3.0 was 2025-06-18 (`https://api.github.com/repos/raspu/Highlightr`, releases list). The recommended successor, `smittytone/HighlighterSwift`, is MIT-licensed, actively pushed (`last push 2026-07-04`), and at version 3.1.0, supporting macOS 11+ (`https://github.com/smittytone/HighlighterSwift`). **Important architectural caveat, inferred but strongly implied by both projects' own docs [I]**: Highlightr/HighlighterSwift wrap **highlight.js via JavaScriptCore** (regex/lexer-based highlighting, not an AST) — this is qualitatively different from tree-sitter: faster to integrate, no incremental-parse infrastructure needed, but syntactically shallower (no symbol-aware structure, no fold/jump-to-definition substrate) and pays a JSCore bridging cost per highlight pass (Highlightr's own README claims "~50ms... for processing 500 lines of code" on a 2015-era iPhone 6s — a real but dated number, flagged as pre-2025 and likely optimistic for large modern files).

## 4. The ChimeHQ ecosystem — Neon, TextStory, SwiftTreeSitter, Rearrange, TextViewPlus

**Is this the de-facto standard layer for native Swift editors in 2026? Yes — with one important organizational correction.** **[V]**

- **`SwiftTreeSitter` has been TRANSFERRED out of the ChimeHQ org.** It now lives at `https://github.com/tree-sitter/swift-tree-sitter` (owner: the official `tree-sitter` GitHub org), confirmed via `https://api.github.com/repos/tree-sitter/swift-tree-sitter` (`"full_name":"tree-sitter/swift-tree-sitter"`). The old URL `github.com/ChimeHQ/SwiftTreeSitter` still resolves and redirects — confirmed by a closed GitHub issue thread, `https://github.com/tree-sitter/swift-tree-sitter/issues/32`, where maintainer Matt Massicotte writes *"It now lives at https://github.com/tree-sitter/swift-tree-sitter, however, https://github.com/ChimeHQ/SwiftTreeSitter still works, and redirects to the new location."* **This is a positive maintenance signal, not decay** — it means the de-facto standard Swift tree-sitter binding graduated into the canonical upstream tree-sitter org, which is a stronger institutional home than a single maintainer's personal org. However, some downstream `Package.swift` files (e.g. Neon's own, `https://github.com/ChimeHQ/Neon/blob/main/Package.swift`) still point at the old `ChimeHQ/SwiftTreeSitter` URL on a `branch: "main"` pin (not a stable version tag) — the redirect makes this work but is worth normalizing in any long-term dependency lock.

- **TextStory** (`ChimeHQ/TextStory`, "Happier, more flexible NSTextStorage"): active, BSD-3-Clause, `pushed_at: "2026-04-22"`. **[V]** This is a direct dependency of `CodeEditTextView`'s `Package.swift` (`from: "0.9.0"`) — confirming Neon/ChimeHQ infrastructure is already load-bearing *inside* CodeEdit's own stack, not a separate competing choice.
- **Rearrange** (`ChimeHQ/Rearrange`, range-type utilities): active, BSD-3-Clause, `pushed_at: "2026-04-28"`, a direct dependency of Neon's `Package.swift`.
- **TextFormation** (`ChimeHQ/TextFormation`, typing-completion rules): active, BSD-3-Clause, `pushed_at: "2026-04-28"` — also a direct `CodeEditSourceEditor` dependency (confirmed in that package's `Package.swift`), reinforcing that ChimeHQ libraries are the connective tissue underneath *both* STTextView (via its official Neon plugin) and CodeEditSourceEditor simultaneously.
- **`TextViewPlus`** (`ChimeHQ/TextViewPlus`, "Make life better with NSTextView+TextKit 1/2"): **noticeably slower** than its siblings. **[V]** `pushed_at: "2024-03-25"` — over two years stale relative to today (2026-07-28), versus the 2026-04-to-2026-07 activity band of every other ChimeHQ repo checked. 51 stars, 1 open issue, not archived but clearly not a maintenance priority. **This is the one ChimeHQ repo in the list that has genuinely slowed**, and should not be relied on as a current integration point.

- **The Chime editor itself**: ChimeHQ (the org) ships its own commercial macOS editor, `ChimeHQ/Chime` ("An editor for macOS"), 477 stars, BSD-3-Clause, `pushed_at: "2026-04-28"` — confirming these libraries are proven in a shipping product built by the same team that authors them, not just theoretical.

## 5. Web-view options — Monaco or CodeMirror 6 inside a `WKWebView`

**Who ships this on macOS in a native-feeling app**: **[V]** Numerous small/indie apps do — the search turned up a cluster of real, shipping Tauri-based macOS Markdown/note apps using CodeMirror 6 inside a `WKWebView`-backed shell: `LMD` (Tauri+React+CodeMirror, `github.com/TaylorChen/lmd`), `Prism` (Tauri+CodeMirror 6, explicitly markets itself as "a quiet, native-feeling Markdown editor," `github.com/AlexPlum405/Prism`), `Noted.` (Tauri+CodeMirror, `github.com/wenujacodes/Noted.`), and `quill` (Tauri 2+CodeMirror 6, `github.com/linyimin0812/quill`). None of these is a terminal-first app the way Umber is; all are markdown/note editors where the editor *is* the whole product, which is the opposite of Umber's "editor is secondary" positioning.

**Concrete, cited costs (not generic FUD):**
- **Input latency / dropped keystrokes**: a real, recent (merged 2026-06-29) bug fix in a production SQL-editor app: *"in WKWebView, finishing a [mouse] drag wedges Monaco's textarea input deduction — the first printable key produces a correct textarea edit but no model edit, so the keypress is lost"* (`Technarion-Oy/thaw`, PR/commit `1989cc7`, `https://github.com/Technarion-Oy/thaw/commit/1989cc7c95f69d29add65e3695b5e51ef58dc4bb`). This is a **2026-dated, first-party bug report with root-cause diagnosis**, not a stale forum complaint.
- **Native key-equivalent / menu handling**: multiple corroborating reports that macOS `Cmd+C`/`Cmd+X`/`Cmd+V` do not flow through WKWebView's native responder chain into web-editor DOM events by default, requiring hand-rolled keydown interception and `execCommand` monkey-patching (`skyhook-io/radar` commit `f67e1cd`, `https://github.com/skyhook-io/radar/commit/f67e1cd4e9ae5eba1d24aa553fe409a579614766`: *"WKWebView does NOT dispatch DOM copy/cut events from the native copy: selector"*). A second, older but illustrative case: Monaco itself has a **years-old open upstream issue**, *"Can't click anywhere except last line, if embedded in WebKit controller on Mac"* (`microsoft/monaco-editor` #1255, opened against WebKit specifically, root-caused to WKWebView's UA string not identifying as Safari — flagging this one as **older/possibly-stale** since the visible activity is 2020-2022, though the underlying WebKit behavior it describes has not been reported fixed).
- **Degrading the "native macOS app" feel — first-party account from a real shipping company**: Craft (the note-taking app) published a detailed postmortem, *"Thinking Outside of the WKWebView"* (`https://www.craft.do/blog/thinking-outside-of-the-wkwebview`), describing exactly this class of problem for their whiteboard feature: *"input/focus handling inside the webview was a two-step process: the webview had to be first responder, and then the input field had to be clicked. This required a user to click two times on any input field to start editing."* Their eventual fix was severe: **spawning a separate, dedicated companion app** just to get a "pure AppKit" WKWebView window with correct focus behavior, because macCatalyst's WKWebView and a directly-embedded AppKit WKWebView behaved differently. This is a **credible, concrete, first-party engineering cost** — not FUD — of the "just embed a web editor" path.
- **Also observed in the wild in 2026**: a Tauri-based Claude Code UI wrapper has an **open, unresolved** issue (`aofp/yume` #7, opened 2026-02-10, last activity 2026-02-23) titled *"Window becomes active but WKWebView is not first responder (keyboard input ignored until click)"* — the same class of bug Craft described, still surfacing in current (2026) cross-platform-shell apps.
- **Memory footprint**: not independently benchmarked in this pass — **[I, unverified]**. The `flutter_monaco` changelog (`github.com/omar-hanafy/flutter_monaco`) states "~30-100MB memory depending on content" per editor instance, but that is a Flutter-webview wrapper's own claim about its own bundling, not a controlled macOS-native-vs-WKWebView-Monaco comparison — flagging this number as **directionally suggestive but not independently verified**.
- **Net read**: WKWebView-hosted editors ship successfully when the *editor pane is the whole app* and the team accepts investing real engineering hours in focus/clipboard/key-equivalent glue. None of the evidence found supports "drop Monaco into a WKWebView and it just feels native" — every real account found required nontrivial custom plumbing to approach native feel, and one (Craft) required a second helper process.

## 6. Vendor-a-proven-engine option — is there a libghostty-analogue for *editing*?

**Short answer: no direct analogue exists for "the" editing engine the way libghostty exists for terminals — the two candidate patterns (embed Neovim, consume a Zed crate) each have a real but different shape, and one is a clear non-starter as of this research.**

### Embedding Neovim over msgpack-RPC (the VimR/Neovide pattern)
- **Feasibility from Swift: proven, with a maintained reference implementation.** **[V]** `qvacua/vimr` ("VimR — Neovim GUI for macOS in Swift") is real, large (6,979 stars), and **actively maintained as of this research**: most recent commit `1e7df5a` merged **2026-07-26**, two days before this research date (`https://api.github.com/repos/qvacua/vimr/commits`), titled "Add 'New Window' option on macOS Dock icon." MIT-licensed. Its own README states it is built with a **modular architecture explicitly designed for reuse**: *"The following Swift packages can be used independently: `NvimView` (SwiftPM module containing an NSView which bundles everything needed to embed Neovim in a Cocoa app, including the Neovim binary and runtime files), `NvimApi` (Synchronous and asynchronous API for Neovim)"* (`https://github.com/qvacua/vimr?tab=readme-ov-file`). This is the closest thing to a genuine "vendor a proven engine" pattern for editing that this research found — a maintained `NSView`-wrapping module purpose-built for exactly this embedding.
- **A real, historical maintenance risk actually surfaced and was resolved**: a filed VimR issue (`qvacua/vimr#996`, *"Nvim 0.9 removes ui_bridge"*) documents that upstream Neovim removed the in-process C-pointer UI bridge VimR originally used, forcing a move to pure msgpack-RPC over stdio — and a community contributor's comment confirms *"Thanks to @georgeharker's contribution, VimR now uses stock Neovim binary"* — i.e., **the dependency risk (needing a patched Neovim fork) was identified and eliminated**; VimR today embeds an unmodified upstream `nvim --embed` binary.
- **What UX this forecloses for a non-Vim user — this is the real cost, not the plumbing.** **[I, but strongly grounded]**: embedding Neovim means every editing interaction — cursor movement, selection, undo, even basic typing in the wrong mode — inherits **modal editing** (Normal/Insert/Visual modes, `hjkl`, `:` command line) unless the host app builds an entire non-modal input-translation shim on top, which defeats the point of embedding Neovim in the first place. This is the single most decisive argument against this path for Umber: the owner's stated bar is "beautiful and user-friendly as hell," and modal editing is a famously high-friction default for the large majority of users who have never used Vim. It also forecloses standard macOS text-editing idioms (click-drag selection feels "off" until Visual mode muscle memory exists; Cmd+arrow / Option+arrow word-navigation needs remapping to feel native).
- **Maintenance of the Swift-side bindings: good** — VimR proper is current (commit dated 2026-07-26, see above). A second, independent architecture write-up (`scopecreeplabs.com`, *"Building a Native macOS GUI for Neovim"*) describes a from-scratch NvimView-style package targeting **macOS 14.0+ and Neovim 0.9+**, using `MessagePack.swift` — confirming the pattern is documented and repeatable beyond VimR alone, though this specific "Trinity" project is a blog case-study, not a linked, verifiable public repo, so it is cited here as **corroborating pattern evidence, not as an installable dependency [I]**.
- **Also relevant**: Neovide (`neovide/neovide`, Rust, not Swift) is the other major embedder of this pattern, actively developed (a merged PR dated 2025-11-18, `neovide/neovide#3296`, fixing CLI passthrough bugs) — confirming the msgpack-RPC-embedding pattern is healthy across language ecosystems, not just a Swift curiosity.

### Zed's editor crates as a consumable library — **explicitly, verifiably NO.**
- **GPUI (Zed's UI framework) is Rust, not Swift — immediately disqualifying for a Swift/AppKit codebase without an FFI bridge.** **[V]** `gpui.rs`, the official docs site, confirms GPUI is "still in active development as we work on the Zed code editor, and is still pre-1.0... you'll also need to use the latest version of stable Rust."
- **Zed's `rope` crate (the core text-storage data structure) is explicitly usable as a standalone Cargo dependency within a Rust codebase** (`[package] name = "rope"` in `crates/rope/Cargo.toml`, `https://github.com/zed-industries/zed/blob/7d42f276/crates/rope/Cargo.toml`) — **but it is licensed `GPL-3.0-or-later`** (verified in the same `Cargo.toml` line: `license = "GPL-3.0-or-later"`), the same copyleft constraint as STTextView, and it is Rust — so it would require a Rust↔Swift C-FFI bridge to use at all, which is a large, unbudgeted integration surface for a 350-LOC-per-file house style.
- **GPUI itself is not officially published to crates.io by Zed** — the packages found there (`gpui-standalone`, `gpui-unofficial`) are explicitly **third-party, unofficial mirrors**: `gpui-unofficial`'s own README states *"This is an unofficial release of Zed's gpui crate, published to crates.io by gpui-unofficial. It is not maintained by the Zed team."* (`https://crates.io/crates/gpui-unofficial`). Zed's own extension system (`docs/src/extensions/developing-extensions.md`, `https://github.com/zed-industries/zed/blob/master/docs/src/extensions/developing-extensions.md`) is a **WebAssembly plugin API** (`zed_extension_api` crate, compiled to `wasm32-wasip2`) — this is for writing *extensions that run inside Zed*, the reverse direction from "consume Zed's editor as a library inside another app," and is explicitly scoped ("most extensions will work properly without any Rust code present... only language server, context server and debugger extensions require custom Rust").
- **An experimental Zed-adjacent embedding spike exists but is explicitly not production-ready and is Rust-in-Rust, not Swift-consumable**: `zed-industries/embedded_gpui` — its own README states *"**Experimental.** GPUI running inside a Wasm component, embedded back into a native GPUI application... Expect sharp edges and breaking changes; nothing here is a supported API yet."* This is a Zed-team spike for embedding GPUI panels inside *other GPUI apps* (a plugin model), not a path to reusing Zed's editing logic from an unrelated AppKit codebase.
- **Verdict, stated plainly per the prompt's instruction to be honest when the answer is "no such thing exists":** there is no Zed crate that a Swift/AppKit macOS app can pull in as a dependency today. The rope data structure is real and battle-tested but is Rust + GPL-3.0; GPUI is Rust + pre-1.0 + not officially on crates.io; the only sanctioned "consume Zed" surface is the WASM extension API, which runs code *inside* Zed, not the reverse.

### Scintilla / ScintillaCocoa — a sixth option this pass originally missed

## 7. Comparable 2026 native-macOS apps — what do they use for their editor pane?

**[V] confirmed stacks:**
- **CodeEdit** (`CodeEditApp/CodeEdit`) uses its own extracted **`CodeEditSourceEditor`** package (self-evidently — CodeEdit is the project that spun `CodeEditSourceEditor`/`CodeEditTextView`/`CodeEditLanguages` out of its own codebase; confirmed via CodeEdit's README "Related Repositories" section explicitly linking all three sibling packages, `https://github.com/CodeEditApp/CodeEdit/`). CodeEdit's own 2024-year-in-review blog post confirms the timeline: *"After introducing our custom ground-up text view package at the end of last year, we continued to improve stability and accessibility"* (`https://www.codeedit.app/blog/2025/01/2024-year-in-review`) — i.e., CodeEdit **did not adopt STTextView or plain NSTextView; it built its own TextKit-1-based (not TextKit-2) text-view stack from scratch**, which the CodeEditTextView README itself frames as intentionally narrower in scope than STTextView (§2).
- **Zed** (`zed-industries/zed`) uses its **own custom Rust text-storage stack**: `Rope` (SumTree-backed, `crates/rope`) plus `GPUI` for all rendering — confirmed extensively via source reads above (§6). Zed's own blog (*"Rope & SumTree — Zed's Blog"*, `https://zed.dev/blog/zed-decoded-rope-sumtree`) explains why: *"One reason for why Zed has its own implementation instead of using a library is that a lot of libraries didn't exist when the Zed founders laid the groundwork for Zed in 2017"* and concurrent multi-threaded access to buffer text was "a hard requirement." Zed is not a Swift/AppKit comparison in engineering terms, but it is a relevant *product* comparison (a fast, native-feeling, GPU-rendered editor) whose lesson is: **the team that could afford to build a from-scratch engine did so because their performance requirements (real-time collaborative multi-cursor editing) were unusually extreme — not a default recommendation.**
- **Nova (Panic)** — **also hand-rolled its own text layout engine**, not TextKit-2/STTextView/CodeEdit-package-based. **[V]** Panic's own public statement (via Hacker News, quoted directly): *"During beta we found some bugs in Apple's text layout engine that we just could not fix. Our solution? Writing our own text layout manager… from scratch."* (`https://news.ycombinator.com/item?id=24495330`, the comment thread beneath it includes informed pushback clarifying this almost certainly means "wrote a custom `NSLayoutManager`/layout coordinator on top of CoreText," not "wrote a text shaper" — flagged here as **[I]** interpretive nuance on top of a **[V]** direct quote). Nova's official site (`nova.app`, checked 2026-07-28, "Download Nova 14... Requires macOS 15.6+") confirms Nova is still actively shipping and updating (version 14, per the live download page) — this is a *current*, not historical, data point. A contemporaneous review (Coyote Tracks, `coyotetracks.org/blog/panic-nova`) independently corroborates the custom-engine claim and its cost: *"With stupid huge files its performance drops noticeably... Panic wrote their own text editing engine for Nova, which is brave, but it needs more tuning for pathological cases."* — i.e., **even a well-funded team (Panic) hand-rolling a text engine still has known, publicly documented performance cliffs on large files.**
- **VimR** — uses the Neovim-embedding pattern (§6), confirmed above, actively maintained as of 2026-07-26.
- **Ghostty (`ghostty-org/ghostty`)** is a terminal, not an editor, but is directly relevant to Umber's "vendor a proven engine behind a protocol seam" house pattern discussion: its own README confirms `libghostty` (the embeddable C library) is explicitly designed for third-party embedding (*"a cross-platform, zero-dependency C and Zig library for building terminal emulators or utilizing terminal functionality... Anyone can use `libghostty` to build a terminal emulator or embed a terminal into their own applications"*) and that the native macOS shell is *"a true SwiftUI-based application... The macOS app is a `libghostty` consumer. The macOS app is a native Swift app developed in Xcode and `main()` is within Swift. The Swift app links to `libghostty` and uses the C API to render terminals."* This is the closest real, working precedent for Umber's own libghostty-terminal-pane probe — but it is a **terminal** engine, and this research found **no editing-equivalent** of comparable maturity (per §6's explicit "no" on Zed and the modal-editing cost on Neovim).
- **Could not determine, and saying so rather than guessing**: Chime's (`ChimeHQ/Chime`) exact editor-view class was not directly confirmed from source in this pass (only that the org builds and depends on Neon/TextStory/Rearrange/TextFormation as libraries, and ships an editor called Chime) — **[I, flagged as unconfirmed]**, it is very likely Chime uses ChimeHQ's own library stack directly rather than STTextView or CodeEditSourceEditor, given authorship, but this was not verified by reading Chime's own source tree (Chime's repo topics list `extensionkit, macos, swift, swiftui, text-editor` and it is 477-star, BSD-3-Clause, `pushed_at: 2026-04-28` — active — but its internal editor-view implementation file was not fetched in this pass). Ghostty-based "workspace" hybrid apps found in this pass (ForkTTY, Fantastty, Maxx/mosttly-ghostty) are all **terminal-multiplexer/workspace tools, not editor-pane apps** — none of them were found to embed a code editor pane at all; they are out of scope for this specific question and are noted here only to be explicit that the search did not surface an editor-plus-terminal hybrid comparable to Umber's own shape other than the general "IDE" category (CodeEdit, Nova).

## 8. UX affordances, not engines — ranked by value-per-implementation-cost for a terminal-first app with a secondary editor

Ranking basis: cost estimate is grounded in what §1-§4 showed is **already present in `NSTextView`/AppKit for free**, what is a **small addition on top of plain `NSTextView`**, and what **requires swapping the engine** (STTextView or CodeEditSourceEditor) to get affordably. Real product behavior is cited per item per the prompt's requirement.

| Affordance | Cost tier | Grounding (real product behavior) |
|---|---|---|
| **Dirty indicator** (unsaved-changes marker) | **Cheap — plain `NSTextView` today.** `NSDocument`'s own `isDocumentEdited` / window's "close dot" is stock AppKit; BBEdit additionally puts a bullet indicator in its sidebar for unsaved docs (*"Unsaved documents in the sidebar have a bullet indicator on the left side"*, BBEdit 15.0 release notes, `barebones.com/support/bbedit/notes-15.0.html`). No engine change needed. |
| **Find & replace** (in-buffer) | **Cheap-to-moderate — plain `NSTextView` today.** `NSTextView`/`NSTextFinder` ships Apple's own incremental find UI; STTextView explicitly re-exposes this with one line (`textView.isIncrementalSearchingEnabled = true`, §1). CodeEditSourceEditor also ships an equivalent `Find/` module (§2) but you do not need to switch engines to get basic find/replace — it's the single cheapest high-value win. |
| **Soft-wrap toggle** | **Cheap — plain `NSTextView` today.** `NSTextView.isHorizontallyResizable` / paragraph-style line-wrapping is stock; STTextView exposes it as a one-line option (`wrapLines`) confirming it's considered a baseline feature, not an engine differentiator. |
| **Line numbers / gutter** | **Cheap *if* you adopt STTextView; moderate if hand-rolled on plain `NSTextView`.** STTextView ships this built-in (`showsLineNumbers = true`, §1) — effectively free once the engine is swapped. Hand-rolling on plain `NSTextView` means writing a custom `NSRulerView` (or overlay view) synced to TextKit 2's async viewport layout, which is exactly the class of pitfall in §3 (ruler/gutter-adjacent bugs FB13290979/FB13291926). BBEdit's own long history of ctags/gutter/fold-indicator bugs (e.g., *"Fixed bug in which in-text fold indicators would draw over the gutter or line number bar while scrolling"*, BBEdit 12.6 notes) confirms this is a real, nontrivial surface even for a 20+-year-mature commercial editor — **do not underestimate this as a "cheap win" on a hand-rolled `NSTextView`.** |
| **Jump-to-line** | **Cheap regardless of engine.** A simple modal/sheet that reads a line number and repositions the selection/scroll is pure application code against any text-storage API (`NSTextView.scrollRangeToVisible`); does not depend on which editor engine is chosen. |
| **Syntax highlighting** | **Moderate-to-expensive on plain `NSTextView`; cheap if STTextView (via its Neon plugin, §1) or CodeEditSourceEditor (built-in, §2) is adopted.** This is the affordance most directly gated by the engine decision — see §3 for why hand-rolling the invalidation/flicker-free layer specifically is the hard part, not the tree-sitter parsing itself. |
| **Format-on-save** | **Cheap, engine-independent** — this is "run an external formatter binary/LSP `textDocument/formatting` request and replace the buffer contents on save," which is application-level orchestration regardless of which text view holds the buffer. |
| **Split view** (two editors side by side) | **Moderate — mostly a window/view-controller layout problem, not a text-engine problem.** Any `NSViewController`-hostable text view (plain `NSTextView`, STTextView, or `CodeEditSourceEditor`'s `TextViewController`) can be duplicated into an `NSSplitViewController`; the cost is state-sync (shared document model, cursor/scroll independence) not the editor engine itself. Nova explicitly advertises this ("All-In-One Design: All of your tools, from editor to terminal to Git, coexist in a single optimized workspace," `nova.app`) as a baseline expectation in 2026-era native editors. |
| **Symbol jump via tree-sitter/ctags** | **Expensive without an engine that already exposes a parse tree.** BBEdit's ctags-based "Go to Named Symbol"/"Find Definition" required decades of accreted, still-being-refined machinery (ctags file generation, relative-path resolution, LSP semantic-token layering as of BBEdit 16.0) — real product evidence this is a deep, ongoing investment even for a mature commercial app, not a weekend feature. CodeEditSourceEditor ships a "Jump To Definition" feature (§2, added release 0.15.0) precisely *because* it already has a tree-sitter parse tree to query — this affordance is one of the strongest arguments for adopting an engine rather than hand-rolling. |
| **Diff-against-git view** | **Expensive, engine-adjacent but mostly a separate subsystem.** Requires a git-diff computation layer plus a rendering mode (inline markers or side-by-side) — CodeEditSourceEditor lists "text diff" as a shipped feature, but this is realistically a distinct feature module layered on top of whichever text view is chosen, not free with any engine. |
| **Breadcrumbs** (file-path / symbol-scope trail) | **Expensive relative to value for a *secondary* editor pane.** This is a symbol-hierarchy-aware UI feature (Xcode-style) that presupposes the symbol-jump infrastructure above already exists — lowest priority for a terminal-first app per the prompt's own framing. |

**The one-sentence ranking**: dirty indicator, find/replace, soft-wrap, and jump-to-line are cheap wins available **today, on the current plain `NSTextView`, with zero engine change**; line numbers and syntax highlighting are the two affordances that most directly justify an engine swap (STTextView or CodeEditSourceEditor); symbol-jump, diff-view, and breadcrumbs are real but expensive, and depend on already having made the engine decision first.
