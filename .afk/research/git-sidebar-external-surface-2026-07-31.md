# External prior art: git/source-control UI in sidebars — VS Code decomposed, competitors, and the UX trap list

Status: FINAL (research-only; no local repo code was read; no code written, per task rules)
Research date: 2026-07-31. All version/date-sensitive claims are marked with a date; unresolved claims are marked **UNVERIFIED**.

**Framing constraint carried through this whole doc:** the target app (Umber) is a terminal. Its user has a shell one keystroke away and can type `git add`, `git commit`, `git diff` themselves. Every judgment below is made against that baseline, not against "what would a GUI-only editor user want."

---

## 1. VS Code's git surface, decomposed into 4 separately-shippable systems

"Git in the VS Code sidebar" is not one feature. It is at least **four independent UI subsystems** that ship together but have almost nothing in common architecturally. Conflating them is the most common mistake in scoping this kind of work.

### (a) The Source Control VIEW — a separate panel, NOT the file tree

Primary sources: `docs/sourcecontrol/staging-commits` and `/overview` (code.visualstudio.com), `api/extension-guides/scm-provider` (code.visualstudio.com), `extensions/git/src/repository.ts` (github.com/microsoft/vscode).

- It lives in its own Activity Bar icon (⌃⇧G), architecturally separate from the Explorer (file tree). **This is the single most important structural fact**: VS Code never puts staging/commit controls inside the file tree. The file tree only gets passive decorations (§1b). Staging is a whole separate view with its own model.
- Resource groups, confirmed directly in `extensions/git/src/repository.ts` (https://github.com/microsoft/vscode/blob/main/extensions/git/src/repository.ts): `merge` ("Merge Changes"), `index` ("Staged Changes", hidden-when-empty unless `git.alwaysShowStagedChangesResourceGroup`), `workingTree` ("Changes"), `untracked` ("Untracked Changes", only split out as its own group when `git.untrackedChanges` is `"separate"` — default bundles untracked into "Changes").
- Commit input: single expandable text box, Cmd+Enter to commit. An AI "generate message" sparkle icon exists in current docs but is a materially later addition bolted onto a much older manual-message design — not evidence that AI assistance is load-bearing to the feature.
- Commit variants confirmed from docs: **Commit** (staged only), **Commit All** (stage-everything-then-commit, via "..." menu), **Undo Last Commit** (via "..." menu). A full-editor commit-message mode also exists (`git.useEditorAsCommitInput`) for long messages.
- Per-resource inline actions, confirmed via the extension API's `scm/resourceState/context` menu contribution point and walkthrough docs: stage (+), unstage (−), discard, open-diff (click opens a diff editor; a newer multi-file diff editor also exists, see `multiDiffEditorEnableViewChanges` in the same source file).
- Overflow "..." menu: secondary + repository-level plumbing (pull/push/fetch/branch/stash/tags).
- Activity-bar count badge: **confirmed directly** in the quickstart doc (code.visualstudio.com/docs/sourcecontrol/quickstart): "The source control icon in the Activity Bar also shows a badge with the number of affected files."
- Branch + sync indicator: lives in the **status bar**, not this view — see §1d.
- The whole view is provider-agnostic (`SourceControl`, `SourceControlResourceGroup`, `SourceControlResourceState` — code.visualstudio.com/api/extension-guides/scm-provider). Git is the built-in implementation; the same view hosts Perforce/SVN extensions.

**Problem solved:** lets a user stage/commit without memorizing `git add`/`git commit`, and gives a pending-changes count without running `git status`.

### (b) Git DECORATIONS in the Explorer tree — a passive overlay on the file tree

Primary sources: `extensions/git/src/decorationProvider.ts` and `extensions/git/src/repository.ts` (github.com/microsoft/vscode).

- Implementation confirmed from source: this is a **separate `FileDecorationProvider`**, layered on top of the tree via VS Code's generic decoration API — it is not a property the tree itself stores. Two providers exist: `GitIgnoreDecorationProvider` (colors only, ignored files) and `GitDecorationProvider` (colors + letter badges, built from the identical four resource groups that back the Source Control view — i.e. **the Explorer decorations and the Source Control view share one underlying model**, just render it in two places).
- **Letter badges, confirmed directly from `Resource.getStatusLetter` in `repository.ts`** (exact switch statement, current `main` branch):
  - `M` — Modified (working tree or index)
  - `A` — Added (index-added or intent-to-add)
  - `D` — Deleted (working tree or index)
  - `R` — Renamed (index-renamed or intent-to-rename)
  - `T` — Type Changed
  - `U` — Untracked
  - `I` — Ignored
  - `C` — Copied (index-copied)
  - `!` — any merge-conflict state (both-deleted, added-by-us, deleted-by-them, added-by-them, deleted-by-us, both-added, both-modified) — comment in source: "Using ! instead of ⚠, because the latter looks really bad on windows"
  - Note: an **older** version of this same file (commit `1ea67719`, exact date not captured) used a different, now-superseded mapping where copied/conflict states collapsed to `C` and there was no `T`/`!` — the table above is the *current* `main`-branch mapping, not a universal constant across VS Code's history. Treat any git-decoration-badge reference you find elsewhere as potentially version-dependent.
- **Color-token mapping, confirmed directly from `Resource.getStatusColor` in `repository.ts`**:
  - `INDEX_MODIFIED` → `gitDecoration.stageModifiedResourceForeground`
  - `MODIFIED`, `TYPE_CHANGED` → `gitDecoration.modifiedResourceForeground`
  - `INDEX_DELETED` → `gitDecoration.stageDeletedResourceForeground`
  - `DELETED` → `gitDecoration.deletedResourceForeground`
  - `INDEX_ADDED`, `INTENT_TO_ADD` → `gitDecoration.addedResourceForeground`
  - `INDEX_COPIED`, `INDEX_RENAMED`, `INTENT_TO_RENAME` → `gitDecoration.renamedResourceForeground`
  - `UNTRACKED` → `gitDecoration.untrackedResourceForeground`
  - `IGNORED` → `gitDecoration.ignoredResourceForeground`
  - all conflict states → `gitDecoration.conflictingResourceForeground`
  - Submodules get a hardcoded badge `'S'` and `gitDecoration.submoduleResourceForeground` (confirmed, `GitDecorationProvider.SubmoduleDecorationData`).
  - `gitDecoration.stageAddedResourceForeground` does **NOT** exist, despite older docs implying it — confirmed by a maintainer fixing the docs in https://github.com/microsoft/vscode/issues/108434 (2020). Staged-added files reuse `gitDecoration.addedResourceForeground`. This is a good example of "confidently wrong secondary sources exist — verify against source."
- **Default hex values — UNVERIFIED against a primary VS Code source file.** I could not locate the canonical `contributes.colors` registration (this lives in `extensions/git/package.json`, a file I did not manage to pull directly) or a `colorRegistry.ts` entry for the `gitDecoration.*` family specifically — VS Code's core `colorRegistry.ts` hosts editor/workbench colors, but the git-specific tokens are registered by the bundled git *extension*, a different file I didn't reach. The following hex values are **only sourced from third-party community gists** (a "VS Code default colors" gist and a CSS-variable dump gist, both unofficial), and are internally inconsistent with each other on `addedResourceForeground`/`untrackedResourceForeground`/`modifiedResourceForeground` (one gist shows flat hex, the other shows rgba-with-alpha, suggesting the second gist was dumped from a *modified* theme, not stock Dark+). Treat all specific hex values below as **[unverified, third-party]**: modified ≈ `#e2c08d` (dark), deleted ≈ `#c74e39`, added/untracked/renamed ≈ `#81b88b`/`#73c991`, ignored ≈ `#8c8c8c`, conflicting ≈ `#e4676b`, submodule ≈ `#8db9e2`. Do not cite these as VS Code's authoritative defaults without pulling `extensions/git/package.json` directly.
- **Folder propagation of a child's dirty state — CONFIRMED via primary source, and the mechanism is precise.** `Resource.resourceDecoration` in `repository.ts`:
  ```
  get resourceDecoration(): FileDecoration {
    const res = new FileDecoration(this.letter, this.tooltip, this.color);
    res.propagate = this.type !== Status.DELETED && this.type !== Status.INDEX_DELETED;
    return res;
  }
  ```
  This is VS Code's generic `FileDecoration.propagate` flag (part of the public decoration API, not git-specific). **Default is propagate = true** — i.e., yes, a parent folder inherits a child's decoration color by default — **except when the child's status is DELETED or INDEX_DELETED**, which explicitly do not propagate up. The original open design question ("which child status should a parent pick up when there are several, e.g. one modified + one untracked child?") is visible being worked out live by the VS Code team in the original 2016–2017 feature-request thread, https://github.com/microsoft/vscode/issues/178 — Atom's prior-art rule cited there (modified beats added; parent dirs colored all the way to project root) matches what shipped. This propagation is also the direct cause of a known, still-open UX complaint: https://stackoverflow.com/questions/72054737 — a user wants color on the *file* only, not every ancestor folder up to root, and there is no such setting (`explorer.decorations.colors` is all-or-nothing).
- **Strikethrough-on-deleted — CONFIRMED via primary source.** `Resource.strikeThrough` in `repository.ts`: `switch (this.type) { case Status.DELETED: case Status.BOTH_DELETED: case Status.DELETED_BY_THEM: case Status.DELETED_BY_US: case Status.INDEX_DELETED: return true; default: return false; }`. Yes — deleted files get literal strikethrough text styling in the tree, confirmed directly in source, not inferred.
- **Known, real performance/correctness failure modes of this exact feature** — collected with citations in §4 below (the "UX trap list").

**Problem solved:** lets a user glance at the tree they already have open and see what's dirty, without running `git status`.

### (c) Editor-adjacent: gutter diff decorations, inline diff peek, and git blame

- Gutter dirty-diff bars (colored marks in the left margin next to changed lines) and inline-diff-peek (click the bar → mini diff popover with revert/stage-hunk) are core, original features — same vintage as the Source Control view itself (`docs/sourcecontrol/overview`: "Additional UI elements: in-context Git information like editor gutter indicators").
- **Native inline git blame is NOT original and is much younger than commonly assumed — this needed explicit verification and the naive assumption ("VS Code always had blame") is WRONG.**
  - Feature request https://github.com/microsoft/vscode/issues/205424, opened **2024-02-17**, shows blame was extension-only for the first ~8 years of the Source Control view's life.
  - A VS Code engineer's own comment on that same issue, dated **2024-11-27**: "In the latest VS Code Insiders you can enable git blame editor decorations and the git blame status bar entry using the following settings: `git.blame.editorDecoration.enabled`, `git.blame.statusBarItem.enabled`."
  - So native blame reached Insiders in **very late 2024**, meaning stable-channel availability is early-to-mid 2025 given VS Code's monthly release cadence — i.e., as of this research (2026-07-31) native blame is **roughly a year old**, not a foundational feature.
  - The extension ecosystem answered this demand *years* earlier: GitLens has had blame-adjacent features for most of its life, and the smaller, non-GitLens `Sertion/vscode-gitblame` extension shipped inline blame messages in **v10.0.0, dated 2022-11-23** (its own CHANGELOG.md) — two-plus years before Microsoft's native version.
  - Community sentiment in the same thread explicitly frames GitLens as "too intrusive" (unwanted upsell nagging) — a a direct data point that a *lighter-weight* blame implementation is valued over a maximalist one, relevant if Umber ever builds this.

**Problem solved:** "what changed in this file, line by line" (gutter/peek) and "who wrote this line and why" (blame) — both contingent on having a real code-editing surface, which Umber's `FileViewerPane` currently is not (per the repo's own "Not Built Yet" list: "no code intelligence").

### (d) Status bar branch + ahead/behind sync indicator

Referenced throughout the docs (`docs/sourcecontrol/overview`) as existing, but I did not pull a page dedicated solely to it in this pass — flagging as **high-confidence-but-thinly-cited**. It shows current branch name and, when tracking a remote, ahead/behind counts; clicking triggers branch-switch or sync actions. This is architecturally the smallest and cheapest of the four systems, and (per the ranking below) arguably the highest-value-per-cost for a terminal.

## 2. Ranked table — value per unit of implementation complexity, FOR A TERMINAL

Judged against: "what does this buy a user who already has a shell one keystroke away," not "what does this buy a GUI-only editor user."

| Rank | Feature | User problem solved | Share of VS Code's total "git" surface area | Implementation cost for an AppKit terminal with an existing NSOutlineView tree | Verdict |
|---|---|---|---|---|---|
| 1 | **Branch name + ahead/behind indicator** (ambient label — window title, tab, or sidebar header) | "What branch, and am I in sync with remote" without repeatedly typing `git status`/`git branch` | Small slice of total UI surface, but very high **frequency of glance** | Very low: one `git symbolic-ref` + `rev-list --left-right --count` shell-out, polled or refreshed on focus | **Highest ROI.** Purely ambient, ready-only, never competes with or duplicates the shell. Same shape of feature as the cwd-follow poller the app already has. |
| 2 | **File-tree decorations (letter badge + color), NOT a separate panel** | "Which files are dirty" while browsing the tree that's already open | Large — the single feature every competitor's own users explicitly and repeatedly ask for (see Warp §3, GitHub Desktop / Sublime Merge tree-view threads §4) | Moderate: needs a git-status model (path → status map, rebuilt on `git status --porcelain` after FS-watch events), a redraw hook into the existing outline-view cell rendering, and careful invalidation — see the whole UX-trap list in §4 for what NOT to copy | **Second-highest ROI.** Reuses the tree that already exists — no new panel, no staging model, no commit-message widget. This is the cheap 80% of VS Code's Explorer-decoration value, IF the traps in §4 are avoided. |
| 3 | **Gutter dirty-diff bars in an editor pane** | "What changed in *this* file, line by line" | Large for editor-centric workflows | Contingent on having a real code-editing surface at all — moot until `FileViewerPane` gains code intelligence (an unrelated, larger roadmap item) | Deferred, not rejected. |
| 4 | **Source Control view (stage/unstage/commit UI, resource groups, commit box)** | Lets a GUI-only user avoid typing `git add`/`git commit` entirely | The single largest visual chunk of "VS Code git," by screen area and by engineering investment | High: an entire new panel, a staging model with 3–4 resource groups, a commit-message input widget with its own keybinding semantics, diff-view wiring, "undo last commit" semantics, merge-conflict handling | **Lowest ROI for this app.** The entire reason this view exists is to give a keyboard-and-CLI-optional path to two commands the target user already has memorized and one keystroke away. Building this is building a GUI git client bolted onto a terminal: highest engineering cost on the list, smallest marginal value over "the user just types `git commit`." |
| 5 | **Inline/gutter git blame** | "Who wrote this line and when" | Real value, but even VS Code shipped it ~9 years after the Source Control view itself (§1c) | Moderate-high: `git blame` parsing, hover UI, per-line annotation rendering | Same gating as #3 — contingent on a real editor pane, and proven NOT foundational even by VS Code's own timeline. |
| 6 | **Full commit graph / history view** | Visual DAG of commits/branches | Recent addition even in VS Code (Source Control Graph shipped as its own view **2024-08-26**, per the milestone-tracking issue #226648 — it replaced an earlier "Incoming/Outgoing" section inside the main Source Control view that users found too noisy, see #224517) | High | Out of scope — this is what Fork/Tower/Sublime Merge/GitHub Desktop exist for (§3). Reinventing it is scope creep into a different product category (a dedicated git GUI client), not "a terminal with ambient git status." |
| 7 | **Status-bar sync counts / push-pull buttons** | One-click fetch/pull/push | Small | Low-moderate | Marginal on its own — mostly duplicates #1's number with an actionable button; only worth adding once #1 exists, and only if clicking beats typing `git pull`. |

**The argument, stated plainly:** a terminal's entire premise is "the shell is one keystroke away." The winning strategy is **ambient status, not workflow replacement**. Ranks 1 and 2 both answer a read-only question — "what's the state of my repo right now" — that costs the user a few seconds of typing to answer manually, especially when the tree is already open and being looked at anyway. Rank 4 (the actual staging/commit UI) answers "let me commit without typing a command," which is **not a problem this specific user has** — they have a terminal in the same window, and the entire reason they chose a terminal-first tool is that they don't mind typing commands. Building a full staging UI would be the single most expensive item on this list while replacing a workflow that costs the target user roughly zero marginal seconds over clicking a checkbox. This is the load-bearing argument for treating (a) as decorative/out-of-scope for Umber and (b)+(d) as the actual ask hiding behind "git in the sidebar like VS Code."

## 3. What other native macOS tools do

### Xcode — has BOTH tree decorations and a separate panel, and is explicitly the origin of the "M/A letter badge, colored bar in gutter" pattern

Sources: developer.apple.com/documentation/xcode/tracking-code-changes-in-a-source-control-repository, .../configuring-source-control-in-xcode.

- **Project Navigator** (Xcode's file tree): "annotates files with changes since the last commit, using an A for new files or an M for modified files" — confirmed directly from Apple's own docs. This predates VS Code's equivalent feature; a 2017 VS Code issue thread explicitly cites Xcode's scheme as the one to copy (github.com/microsoft/vscode/issues/36912: "It's the exact same scheme used by Atom and Xcode too").
- **Source editor gutter**: a colored "change bar" — blue = local uncommitted change, gray = committed-locally-but-not-pushed, red = conflicts-with-upstream, blue outline = someone else's upstream change (blorenzop.medium.com/how-to-use-git-with-xcode, corroborated by developer.apple.com docs and a 2018 blog, meandmark.com). Clicking the bar gives a popover to stage/discard/show — **but not commit directly from the gutter** ("For some reason you can't commit changes from the editor. You can only discard changes" — meandmark.com, 2018).
- **Source Control navigator** (separate panel, analogous to VS Code's Source Control view): Changes tab for staging, Repositories tab for branches/tags/stashes, full commit history browsing.
- **Blame**: `Show Last Change for Line` context-menu item, confirmed via jamesdempsey.net (2017) and Apple's own docs — this is Xcode's *native, original* blame feature, not a bolt-on, and predates VS Code's native blame by many years. Notably Apple **renamed it away from "blame"** in Xcode 9.3 (2017-2018) specifically to remove the pejorative connotation — "Blame View" → "Authors View," "Show Blame For Line" → "Show Last Change For Line." Worth carrying forward as a naming precedent if Umber ever ships this.
- **Xcode + git worktrees is a known, long-standing, still-partially-broken combination** — directly relevant since the target repo (Umber's own) uses worktrees heavily:
  - Apple's own bug tracker (openradar-mirror #16877, filed 2017, Xcode 8.x): "When one opens an Xcode project from a git worktree, source-control features don't work" — Blame, Comparison, Log, Project Navigation source-control filter, and the whole Source Control menu are all listed as broken. **UNVERIFIED whether this is fixed in current Xcode** — the mirrored radar has no confirmation of a fix, and a commenter in 2026-era threads is still asking the same "best practices for avoiding conflicts" question (developer.apple.com/forums/thread/833677, undated but recent), suggesting the underlying tension (Xcode's DerivedData/SPM cache is keyed by absolute path, and two worktrees of the same repo have different absolute paths) is structurally still present even if some Source Control panel bugs were fixed.
  - The practical developer response has been to treat this as a *feature*, not purely a bug — multiple 2020-2022-era blog posts (medium.com/@adityadaniel, paul-samuels.com, notes.adityadaniel.com) recommend git worktrees specifically *because* Xcode's path-keyed DerivedData means each worktree gets an independent build cache, avoiding cross-branch cache pollution.

### Nova (Panic) — dedicated Git Sidebar (separate panel) + gutter change bars + inline author annotations; explicitly does NOT put status in the file tree

Source: help.nova.app/git/sidebar/, help.nova.app/settings/git/, nova.app/releases (changelog).

- The **Git Sidebar** is a fully separate sidebar tab (like VS Code's Source Control view), with three view modes: Repository View (branches/tags/remotes/submodules), Changes View (stage/commit, tree-or-list toggle, "Show Ignored Files" toggle), History View (commit graph with author avatars).
- Nova's **Files Sidebar** (its file tree) — per its own marketing copy (nova.app homepage, bundl.run review) — DOES show git-status color coding: "The Files sidebar shows git status with color-coded file states (modified, added, ignored)" (per a third-party review site, bundl.run, **not Nova's own docs** — flagging as lower-confidence than the Git Sidebar claims, which are sourced directly from help.nova.app).
- **Inline author annotations** (their term for blame) are opt-in, off some defaults, and Nova's own docs explicitly warn about performance: "Displaying these annotations requires Nova to look up the blame status for the current line, which can be CPU-intensive in larger repos. In these cases, you may want to disable author annotations to improve performance" (help.nova.app/editor/overview). This is a direct, first-party admission that blame-on-every-line-change is a real perf cost — relevant corroboration for treating blame as non-trivial engineering, not a free add-on.
- Changelog evidence of real bugs even in a mature, native (non-Electron) implementation: "Git: Sidebar now only reloads its contents if the branch or current HEAD commit of the repository changes" (a fix for over-eager refreshing) and "Git: Resolved a potential crash when performing editor Diff operation" (nova.app/releases) — i.e., even a from-scratch native git integration accumulates refresh-correctness and crash bugs over time.

### Zed — native git panel (separate) + native file-tree decorations WITH a letter-badge option + native inline blame; useful as the newest "built it from scratch, no VS Code baggage" data point

Sources: zed.dev/docs/project-panel, zed.dev/docs/git, zed.dev/blog/git, zed.dev/blog/git-blame-beachball, github.com/zed-industries/zed PRs #10398/#10632/#50216.

- **Project Panel** (file tree) git integration is a **setting, not a given**: `project_panel.git_status` (default **true**) tints file/dir names to reflect status; `project_panel.git_status_indicator` (default **false**) additionally adds a letter badge — M/A/D/U/!(conflict) — confirmed directly in zed.dev/docs/project-panel. **Notably the letter-badge option defaults OFF while the color tint defaults ON** — Zed's own product decision is that color alone is the default experience and explicit letters are opt-in extra verbosity. This is a data point worth weighing against VS Code, which ships both on by default.
- **Git Panel** (separate view, analogous to VS Code's Source Control view): branch/repo state, staged/unstaged tree-or-flat toggle, `[·]`-checkbox staging, `git: commit` command. Confirmed in zed.dev/docs/git.
- **Native git support is recent for Zed too** — "Native Git support in Zed" blog post (zed.dev/blog/git) frames it as a new capability ("today, Git support is now available starting from Zed v0.177!" — exact calendar date not captured in this pass, flagging as **UNVERIFIED date**, though the PR history below anchors it to April 2024).
- **Inline git blame shipped via PR #10398, opened 2024-04-11, merged 2024-04-15** — enabled by default 24 hours later via a follow-up PR #10632 (2024-04-16). This is a genuinely fast, deliberate ship (4 days from open to default-on), useful as a contrast to VS Code's multi-year gap between "Source Control exists" and "native blame exists."
- **Real, first-party-documented performance failure from shipping blame too eagerly**: zed.dev/blog/git-blame-beachball — "Fixing the Git Blame Beachball." Root cause, in Zed's own words: blame was assumed to be open in "one or two files at a time," but once enabled for *every* open file, "every time I changed the git index by committing, Zed would spawn 257 git processes simultaneously" (with 257 files open in one user's session) — a literal beachball/hang. Fixed in v0.133.7. This is the single most concrete, first-party "we shipped blame and it broke" data point in this whole research pass, and a strong argument for gating any future Umber blame feature behind "currently visible file only," never "every open file."
- A **still-open** 2025-11-20 PR (#43173, github.com/zed-industries/zed) references a related unresolved bug: large repos with long git histories still hit "the 95%+ CPU bug" from inline blame, and the fix (project-level `git.inline_blame` override) had no maintainer review activity for 3.5 months as of the last comment — i.e., this class of bug is not fully closed even ~2 years after the original fix.

### Sublime Text / Sublime Merge — a genuinely useful negative case: Sublime Merge (the git-specific tool) explicitly has NO tree view for changed files, and its own userbase has been asking for one since 2019 with no fix

Sources: sublimemerge.com/docs/getting_started, github.com/sublimehq/sublime_merge/issues/418 (opened 2019-03-14, still open as of a 2025-06-17 comment), multiple forum.sublimetext.com threads.

- Sublime Merge's UI is: a repo overview (branches/tags/remotes/stashes), a commit graph, and a **flat file list** for the selected commit/working-tree state. There is a separate "Tree" toggle, but per direct user testimony (Hacker News thread, news.ycombinator.com/item?id=23311093, and multiple `sublimehq/sublime_merge` issues) that Tree view shows the **entire repo's file tree at that commit**, not a filtered tree of *only the changed files* — i.e., it does not solve the problem users are asking for.
- Direct user quotes are unusually blunt and specific about why a flat list fails at scale: "It is listing the full path for all files and truncating the paths if they are too long" (forum.sublimetext.com/t/rework-files-tab); "for large projects with hundreds of touched files per commit scattered across a deep directory hierarchy the current flat list file view is a disaster to work with" (forum.sublimetext.com/t/sublime-merge-some-missing-features, 2021); no multi-select for staging is called out as compounding the same problem (same thread) — you must stage/discard files one at a time in a long flat list.
- This is a **six-plus-year-open, still-unresolved** feature request in a paid, actively-developed, git-*specialist* tool (not a repurposed editor) — strong evidence that "just show changed files in a flat/tree list well" is nontrivial UI work that a small, focused team can leave unaddressed indefinitely without losing customers, i.e., it is not make-or-break for a git client's core value proposition.

### Fork, Tower, GitHub Desktop, Sublime Merge — the dedicated-git-GUI-client category, for calibration

These exist specifically to do what §1's Rank-4/6 items (staging UI, commit graph) do well, and are the correct comparison set if Umber ever wants that scope — but are **out of scope for "git in a terminal's sidebar"** per the ranking argument above. Notable, specific findings:

- **GitHub Desktop explicitly and repeatedly refuses to add a file-tree/explorer view at all** — this is a deliberate product boundary, not an oversight. Direct maintainer quote, closing issue #15041 (2022-07-27): "GitHub Desktop is not intended to be a file browser -- that's why we make it easy to launch into your favorite text editor or file manager." And closing #19609 (2024-11-26): "viewing the files and/or file structure of a repository is not in the scope of GitHub Desktop." This is a **first-party, explicit statement that a git tool need not include a file browser at all** — directly relevant precedent for scoping Umber's decision the other way (Umber already has the file tree; the question is only whether to decorate it).
- **GitHub Desktop's own Changes list is a flat list, not a tree**, and has been for its entire v2 existence — the tree view that v1 had was *removed* in the v2 rewrite (confirmed via a Stack Overflow answer citing desktop/desktop#5468, and independently via the malcolmhardie.com blog post which screenshots the removed v1 tree UI). The oldest tracking issue asking for it back (#2417) was opened in **2017** and remains **open in 2026** with continued user pushback ("This is simply not true" — a user directly disputing the maintainers' 2017 claim that "the current changes list generally seems to be working for folks"). A newer duplicate (#20624, opened 2025-06-11) is also still open as of a 2026-03-07 comment. **This is the single clearest "we deliberately said no to a tree view for 8+ years despite continuous user demand" data point found in this whole research pass** — worth internalizing: a flat list is a legitimate, sustained, deliberate product choice, not merely an underfunded gap.
- **Tower, Fork**: both are commercial, native (non-Electron on macOS) clients with a Changes-view-plus-commit-graph model similar to Sublime Merge's; comparison articles (git-tower.com/blog/best-git-client, thesoftwarescout.com) consistently praise their "undo anything" (Tower) and native-performance/speed (Fork) as differentiators, and consistently note **Git worktree support only shows up as a named feature list item for Tower and GitKraken**, not Fork or Sublime Merge in the sources checked — i.e., worktree-aware UI is still an uneven, non-universal feature even among specialist git GUIs as of 2026.

### Warp — the single most directly-relevant data point: a well-funded "AI terminal" competitor that has NOT shipped tree decorations despite explicitly wanting to

Sources: docs.warp.dev/code/code-review/, github.com/warpdotdev/warp (issues #8969, #11594, #9587; PRs #11938, merged 2026-06-18).

- Warp **does** have a dedicated "Code Review panel" (separate from its file tree/"Project Explorer") — a diff-review UI with staged/unstaged awareness, opened via a chip in the terminal input or a toolbar button. This is architecturally Warp's version of §1(a) — a separate panel, not a decorated tree — reinforcing that even a from-scratch competitor lands on the same "diff review is a distinct surface from file browsing" architecture VS Code and Nova use.
- Warp **has** a branch+ahead/behind status chip — PR #11938, opened 2026-05-30, **confirmed MERGED 2026-06-18** (resolving the earlier UNVERIFIED flag from my first draft). This is Rank-1 from §2, and it took Warp a dedicated PR with 864 added lines across 18 files and a subsequent styling-consistency bug (#13347, chip rendered visibly larger/differently-padded than sibling chips) to ship even this "simple, ambient" feature correctly — evidence that even the cheapest item on the ranked list is not zero-cost.
- **Warp's file tree ("Project Explorer") has NO git-status decorations, and this is an open, actively-tracked, user-requested, maintainer-acknowledged gap as of this research:**
  - Issue #8969 ("File Explorer: Add git status highlighting for modified/untracked files"): "The File Explorer (project sidebar) currently shows no visual indication of git status. All files appear the same regardless of whether they are modified, staged, or untracked... similar to VS Code, Cursor, or iTerm2." **Open.**
  - Issue #11594 ("Add git status decorations to Project Explorer file tree"): a maintainer-triaged design doc that **explicitly cites `microsoft/vscode`'s own `decorationProvider.ts` as the reference implementation to copy** — direct quote from the triage: "VS Code gates these decorations behind theme color keys... Source: https://github.com/microsoft/vscode/.../decorationProvider.ts". This is a striking finding: Warp's own engineers, in 2026, looked at VS Code's exact source file (the same one cited throughout §1b of this document) as the model. **Open, not yet implemented.**
  - Issue #9587 ("Project Explorer: add Git status file tree for current branch (multi-repo + worktrees)"): explicitly cites "VS Code Source Control / JetBrains Commit sidebar style" as the reference UX, and **explicitly scopes in git worktrees as a required case**: "If the workspace includes multiple Git roots or worktrees, see separate/clear change sets per repo/worktree." **Open.**
- **Conclusion: a well-funded, actively-developed 2026-era "AI terminal" with a dedicated diff-review panel still does not have file-tree git decorations, and its own engineering team's design notes point at literally copying VS Code's provider model.** This is strong, first-party evidence that (b) tree decorations is real, wanted, technically nontrivial, and has been deprioritized behind other work even by a team explicitly building "a terminal that replaces IDE context-switching."

### Ghostty — VERIFIED: no official git UI of any kind; it is an open, unimplemented community ask; only unofficial forks show a bare branch name

Source: github.com/ghostty-org/ghostty/discussions/13054, and 9 near-identical community forks (tomreinert/ghostty and its many downstream forks: pacaya, billxc, Hankyone, BUNotesAI, KaimingWan, woop, ttt132, caseman72).

- Official `ghostty-org/ghostty` has **zero** git UI. This is directly confirmed by an **open** (as of this research), unimplemented feature request: discussions/13054, "Feature request: project and Git management sidebar" — explicitly framed by the requester as wanting something in the spirit of another tool ("Otty") that Ghostty does not have, with the explicit acknowledgment "I don't expect a 1:1 copy."
- Multiple **unofficial, personal forks** (not the real Ghostty; each README says so explicitly) add a sidebar that replaces the native tab bar with rich tab cards showing, among other metadata, **git branch name only**: "git branch detected automatically, no setup needed." None of the ~9 forks checked implement a staged/unstaged file list, diffs, or commit UI — confirmed by reading each fork's own README, which is otherwise detailed down to CLI flag names.
- The closest any fork gets to a real git *workflow* feature (not status *display*) is `billxc/ghostty`'s "Super Ghostty," which adds **git-worktree creation from a right-click on a project in the sidebar** — this is worktree *management* tooling, a materially different feature from git *status* tooling (diffs/staging), and worth distinguishing precisely.
- **Plain-language finding, as requested: essentially nobody has shipped real git-status UI in a terminal.** The official project has none and it's an open ask; the enthusiast forks stop at "show the branch name as one line of tab metadata."

## 4. The UX trap list — what specifically goes wrong with git-status-in-a-file-tree

All items below are drawn from real, cited issue threads (primarily `microsoft/vscode`, the most heavily-used and heavily-reported implementation of this exact feature).

1. **Performance collapse at scale, with a specific, quantified failure mode in large multi-root workspaces.** github.com/microsoft/vscode/issues/318279 (opened ~2026-05, still being resolved): opening a ~50-git-repo multi-root workspace kills and restarts the extension host in a loop, root-caused in the companion PR #318862 to `Model.openRepository()` firing a **fire-and-forget `repository.status()` per repo**, each of which fans out **~8 concurrent git subprocesses**; for 50 repos that's ~400 in-flight subprocesses plus a large blocking parse burst on a single thread, which starves the process's own IPC heartbeat. The fix (merged) was a hard concurrency limiter (`Limiter(5)`). **Directly relevant to Umber**: this is the generic "N repos/worktrees open at once" case, and Umber's whole premise is heavy worktree use.
2. **A separate, specific decoration-event cap that silently degrades correctness under load, not just speed.** github.com/microsoft/vscode/issues/108292 ("Git changes inside folders are not revealed in explorer"): VS Code caps decoration-provider events at ~250 entries per push (`ExtHostDecorations`); when a repo has >250 pending decorations, the provider gives up on itemizing them and fires one big "everything changed" event instead — but the Explorer only re-queries decorations for currently-**visible** rows, so anything inside a still-collapsed folder is silently never refreshed until the user manually scrolls through it. This is a genuinely subtle bug class: "it looks fine because I already expanded everything once" masks that fresh collapsed folders are stale.
3. **`node_modules`/`.gitignore` churn causes real, reported freezes**, not just cosmetic slowness. github.com/microsoft/vscode/issues/97731 ("VS code freezes when typing and scrolling") — root-caused by a VS Code engineer directly in-thread to "a massive decoration change" from an untracked `node_modules` (or similarly large ignored directory) not yet in `.gitignore`; multiple independent reporters in the same thread confirm the fix is adding the offending directory to `.gitignore`, which stops git from reporting thousands of untracked-file decorations at once. A related but distinct 2020-era ignored-file coloring bug (#227057) further shows the two overlapping failure surfaces (ignored-detection bugs vs. genuine perf collapse) get conflated by users reporting symptoms.
4. **Monorepos hit two distinct, separately-filed problems**: (a) the same decoration-cap/perf collapse as node_modules above, at even moderate scale (github.com/microsoft/vscode/issues/313860, "Built-in git extension became unbearably slow" — 15 seconds to render a graph view, 12 seconds for a blame hover, on a **3,272-file** repo, i.e. not even an extreme case); and (b) a **deliberately-shipped, explicitly-scoped-out feature gap**: "Untracked Folders" (#169253) — VS Code's own engineers explicitly chose *not* to build folder-level untracked-file aggregation for large monorepos because `git status -uall` (all untracked files individually) is measurably slower than `git status -uno`, and the "correct" fix (a new resource-group concept for untracked *folders*, not files) was scoped, prototyped, and then explicitly shelved: "We have decided to table this effort for the time being while we better understand the changes that are needed to the VS Code extension API" (2023-01-17 comment, still `*out-of-scope` labeled as of the last update captured).
5. **Submodules are a persistent, multi-year source of "stage/discard silently does nothing" bugs**, not just display glitches. github.com/microsoft/vscode/issues/205125 ("Discard Changes and Stage Changes don't work for submodules") and #211508 (nearly identical, different repro) — root cause identified in-thread: the resolver that maps a resource URI back to "which open repository owns this" (`getOpenRepository`) explicitly walks the list of open repositories and *excludes* any path inside a submodule unless that submodule is *also* separately opened as its own repository — so closing a submodule's own repository silently breaks staging for it from the parent, with **no error surfaced to the user** (buttons just do nothing, no output in the Git log channel). A third-party extension (GitLens) has an independent, still-open, structurally similar submodule staleness bug of its own (eamodio/vscode-gitlens#1437, maintainer reply: "Unfortunately GitLens doesn't have real support for submodules right now").
6. **Git worktrees — directly relevant, since Umber's own repo uses them heavily.**
   - Multi-repository/worktree display is a genuinely new (**2025-12-18**) VS Code feature (PR #284224, "Git - add worktrees node to the Repositories view"), not a mature one, and its own post-ship test pass (#285964, closed 2026-01-05) generated **at least 14 immediately-filed follow-up bugs** in the same session (linked issues #286081 through #286275) — e.g., "Creating a worktree from a worktree node nests worktree folders," "Original tree shows all worktrees top-level in Repositories but a worktree doesn't," "Deleting a worktree in the active worktree window causes error." This is unusually strong evidence that worktree-aware UI is *hard to get right even for the team that owns the whole codebase*, not evidence of a lagging community feature.
   - A **currently open** (as of this research) correctness bug directly matches Umber's stated architecture: #313526, "'Close Other Repositories' is non-functional for worktrees — they reappear immediately" — filed by a user whose explicit workflow is "one window per worktree," i.e. exactly Umber's model (one Space = one project root; the plan doc frames worktrees as a load-bearing concern). The reporter's root-cause analysis, confirmed by VS Code's own git-extension trace log they attached, shows the auto-discovery pass re-adds a manually-closed worktree entry within ~1 second, with a maintainer response acknowledging a deeper issue: any extension (they name GitLens specifically) that resolves git state for a URI inside a closed worktree can "effectively undo Close Repository," because the closed-repository state isn't actually authoritative.
   - #320749 ("detect newly added worktrees without requiring window reload," open): creating a worktree from an **external terminal or tool** (exactly how a coding agent, or a human running `git worktree add` outside the app, would do it) is invisible to VS Code's Source Control Repositories view until a full window reload — the reporter explicitly connects this to agent workflows: "Worktrees are increasingly used by coding agents and parallel development tools... the Source Control Repositories view does not update until a reload, which makes the UI look stale."
   - Xcode's worktree brokenness is covered separately in §3 (openradar #16877) and is a second, independent data point that "IDE + worktrees" is a recurring hard problem, not a VS-Code-specific one.
7. **Sparse checkout is a smaller but real, currently-open gap**: #213677 ("Add sparsed file automatically on a git commit in sparse-checkout repository," 31 👍, still open) — committing a newly-created file via VS Code's Source Control UI in a sparse-checkout repo fails with a raw, un-translated git error ("paths ... matched paths that exist outside of your sparse-checkout definition"), because VS Code's `git add` invocation doesn't pass `--sparse`; the same operation works fine via the CLI or via GitHub Desktop (explicitly noted by the reporter as a comparison point). This is a "we didn't handle a git edge-case flag" bug class, distinct from the perf/staleness bugs above.
8. **The stale-decoration problem is not one bug but a recurring *class* of bug, with at least five separately-filed, separately-root-caused instances found in this pass**: (i) decorations flashing then disappearing on initial folder-open until the Source Control view is manually refreshed (#43606, 2018, closed for lack of repro info — i.e. never actually fixed, just went stale itself); (ii) a second-root-folder-in-a-multi-root-workspace losing its decorations entirely, traced by a VS Code engineer directly to two competing decoration providers (git-status vs. git-ignored) racing and the `undefined` result of the second silently overwriting the first (#48502, "Git has two decoration providers: status and ignored... That `undefined` seems to overwrite the initial status decoration. I thought they'd get merged?" — a maintainer's own words expressing surprise at their own system's behavior); (iii) decorations frozen after a large-file-count transient (re-clone/checkout momentarily reporting everything as deleted) permanently trips a "repository too huge" safety flag with **no recovery path except restarting the whole app** (#322337, dated 2026, i.e. still current); (iv) stale "incoming changes" decorations after a pull, filed directly by a VS Code core engineer against their own product (#205198, "jrieken... it happened twice today that I have seen stale decorations, e.g after pull") — notable because even the team's own daily-driver usage surfaces this; (v) decorations depending on a symlinked repo root breaking entirely (multiple corroborating comments under #70963 and the Stack Overflow thread for the analogous gutter-indicator bug).

**Overall pattern across all eight trap categories**: nearly every failure is a **staleness or a synchronization** bug — the decoration model diverges from actual git state and nothing forces a reconciliation — rather than a rendering bug. This should directly inform an implementation for Umber: prioritize a simple, aggressively-correct invalidation model (rebuild the whole status map from `git status --porcelain` on every trigger, rather than trying to diff/patch it incrementally) over a cleverer incremental-update scheme, because every incremental scheme found in this research (VS Code's decoration-event capping/merging, its two-competing-providers race, its "huge repo" latch) is exactly what produced the staleness bugs.
